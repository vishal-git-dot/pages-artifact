# Page Archive

A self-updating catalog of full page examples — feedback pages,
landing pages, empty states, onboarding flows, and whatever
categories you add next. Drop a page in, push, and a real
screenshot, title, and category show up in the gallery on their
own — nothing to hand-edit.

**This runs entirely on GitHub Pages via GitHub Actions. You never
need to install Node, Playwright, or anything else on your own
machine** — every screenshot is captured by CI, on GitHub's
servers, not your laptop.

## Quick start — no local installs

1. Push this folder to a new GitHub repository, as-is.
2. In that repo, go to **Settings → Pages → Build and deployment →
   Source**, and choose **GitHub Actions**. (This one click can't
   be done from a workflow file — it's the only manual step there
   is.)
3. That's it. The push itself already triggered the workflow; check
   the **Actions** tab. When it finishes, your site is live with
   all 8 example pages screenshotted and cataloged.

From here on, adding a page is still just: create the folder, give
it a `<title>`, push. No command ever needs to run on your computer.

## How the automation works

Unlike a typical "static site + JSON file" gallery, nothing about
the catalog is hand-maintained, and nothing runs locally. On every
push, GitHub Actions spins up a fresh Ubuntu machine, installs
Playwright's Chromium there, and runs `scripts/generate.js`, which:

1. Scans `pages/<category>/<page-id>/` for `index.html` files.
2. Reads each page's own `<title>` and `<meta name="description">`
   — that's the card copy. No separate registry to edit.
3. Derives the category label from the folder name
   (`empty-states` → "Empty States"). A brand-new category needs no
   registration anywhere — just a new folder.
4. Screenshots each page with Playwright, navigating directly to its
   `file://` path (no local server needed) at a fixed 1280×800
   viewport, and saves `thumbnail.png` next to it.
5. Writes `data/pages.js` — a plain `const PAGES = [...]` — which
   `index.html` loads with a `<script>` tag, not `fetch()`, so the
   gallery never depends on an async request that can fail.

**If a page folder is malformed — no `index.html`, no `<title>` —
the build fails loudly with the exact path and what's wrong,**
instead of silently leaving that page out of the gallery. Check the
**Actions** tab if a push doesn't show up.

Nothing generated is committed back to git by CI — the screenshots
and `data/pages.js` exist only inside that run's temporary machine
and in the deployed Pages artifact. The deployed site is built
fresh from whatever's in `pages/` on `main`, every single time, so
there's nothing that can drift out of sync between a push and
what's live, and no second workflow ever needed to "catch up" a
stale file.

## Adding a page

1. Create `pages/<category>/<page-id>/index.html` (plus `style.css`
   / `script.js` if you need them). Reuse an existing category
   folder, or start a new one — it becomes its own gallery section
   automatically.
2. Give it a real `<title>` and a `<meta name="description">`.
   That's exactly what shows on its card.
3. Push to `main`. GitHub Actions does the rest — nothing to run
   yourself.

## Project structure

```
index.html                    Landing page + gallery
assets/
  css/
    tokens.css                 Design tokens
    main.css                   Landing page + gallery styles
  js/
    main.js                    Gallery render / filter / search
data/
  pages.js                     AUTO-GENERATED by CI — don't hand-edit
scripts/
  generate.js                  Scan, validate, screenshot, write data/pages.js
pages/
  <category>/
    <page-id>/
      index.html
      style.css
      script.js
      thumbnail.png            AUTO-GENERATED by CI — gitignored
```

## Deploying to GitHub Pages

`.github/workflows/deploy.yml` runs on every push to `main`:
checkout → install deps → install Playwright's Chromium → run the
generator → strip out `node_modules` (it's only needed to run the
generator, not to serve the site) → deploy. One job, one workflow,
no race with anything else, no step that depends on anything from
your machine.

One-time setup after pushing this repo to GitHub:

1. Go to **Settings → Pages**.
2. Under **Build and deployment → Source**, choose **GitHub
   Actions**.
3. Push to `main`, or trigger it manually from **Actions → Generate
   screenshots & deploy to GitHub Pages → Run workflow**.

The first successful run prints your site's URL in its summary,
typically `https://<username>.github.io/<repo>/`.

## Optional: previewing on your own machine before you push

You never have to do this — it's purely a convenience if you want
to see a page's real thumbnail before pushing, rather than waiting
for CI. Skip this section entirely if you're fine letting GitHub
Actions be the only thing that ever runs the generator.

```bash
npm install
npx playwright install chromium   # one-time browser download
npm run generate                  # screenshots every page + writes data/pages.js
```

Then open `index.html` directly in a browser — no local server
needed, same as the deployed site. Until you run `npm run generate`
for the first time, `data/pages.js` is a committed placeholder
(empty arrays), so the gallery loads fine and just shows an empty
state rather than a broken page.
